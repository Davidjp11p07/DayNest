1. Propósito y alcance

DayNest es una aplicación web en Java conectada a PostgreSQL que permite publicar inmuebles para alquiler por días, buscar alojamientos, reservar, registrar pagos simulados y gestionar giros simulados al propietario. La interfaz distingue visitante, cliente, propietario y administrador. Una identidad puede reunir perfiles de cliente y propietario; el administrador se provisiona fuera del registro público.

Este informe documenta el código actual y reúne los diagramas de casos de uso, clases, interacción mediante secuencias y actividades exigidos por el enunciado. Añade el modelo de base de datos como soporte del diseño. Los PDF de clase se utilizan como guía de notación y fichas; no constituyen una rúbrica exhaustiva del profesor.

El alcance financiero es académico y local: aprobar un cobro, devolverlo o ejecutar un giro registra una simulación en la base de datos. No hay pasarela, banco ni conversión monetaria. La comisión es configurable (10% en la configuración actual) y su porcentaje e importe se conservan en cada giro. Las fotografías son ilustrativas locales asignadas por identificador; no hay subida de fotos, reseñas, recuperación de contraseña o edición de perfil implementadas. La clasificación tipo/campo/mar sí es persistida, puede estar pendiente y se modifica por el propietario.

El recorrido principal es navegador → servlet → service → DAO JDBC → PostgreSQL. Las JSP muestran resultados preparados por los servlets. Las interfaces permiten desacoplar contratos de negocio y persistencia. ServicioBase concentra operaciones comunes; UnidadTrabajoDaoJdbc entrega un contexto Daos con una misma conexión, confirma al terminar y revierte ante error.

La arquitectura tiene detalles concretos: CatalogoService consulta CiudadDao; BloqueoService y HistorialAnteriorService son clases de servicio propias, no implementaciones de interfaces inventadas. Algunas implementaciones instancian CiudadDaoJdbc o UsuarioDaoJdbc directamente. Los diagramas conservan esas dependencias donde se muestran, sin afirmar una inyección de dependencias uniforme inexistente.

4. Modelo de datos y reglas

El esquema operativo daynest contiene 13 tablas: usuario, cliente, propietario, administrador, pais, division_administrativa, ciudad, inmueble, ocupacion, reserva, bloqueo, movimiento_pago y giro. Son la transformación del SVG conceptual más la relación asociativa RESERVA y las extensiones autorizadas OCUPACION/BLOQUEO. El SVG original del profesor se conserva sin cambios; la ampliación tipo/entorno se explica en el modelo lógico.

Usuario tiene especialización parcial y solapada en la BD; Java la implementa con composición de perfiles. Ocupacion tiene subtipo reserva o bloqueo, total y disjunto, comprobado al confirmar la transacción. El calendario usa intervalos [inicio, fin): el día de salida no se ocupa. La exclusión GiST evita cruces entre ocupaciones activas, incluidas reservas pendientes y bloqueos.

El catálogo precargado contempla 32 capitales colombianas y Cartagena, Murcia, España. Las etiquetas muestran ciudad, región y país; los identificadores distinguen homónimos. La búsqueda por texto normaliza tildes y mayúsculas. Los importes conservan COP o EUR según la reserva y se resumen por moneda.

ReglaDiseño implementado
ImporteTotal pactado = noches × tarifa histórica
SaldoTotal pactado − (cobros aprobados − devoluciones aprobadas)
ReservaEntrada posterior a hoy, salida mayor, huéspedes positivos dentro de capacidad
VencimientoPENDIENTE_PAGO vence a los 30 minutos; proceso cada 60 segundos libera fechas
ConfirmaciónPago completo; el botón liquida el saldo y simula aprobación
CancelaciónSolo pendiente/confirmada antes de entrada; libera ocupación y simula devolución si corresponde
BeneficiarioPropietario pactado histórico; un cambio posterior de dueño no lo reemplaza
GiroSalida cumplida, reserva confirmada/finalizada, pago completo y ausencia de giro vigente; neto menos comisión histórica
ClasificaciónTipo y entornos opcionales; NULL es pendiente, no se deduce de ubicación/fotos
HistorialNo se borran contratos y finanzas; public conserva el archivo del modelo anterior

Actores e iniciador: Visitante

Propósito: Crear una identidad con perfil cliente, propietario o ambos.

Precondiciones: No tener sesión iniciada; correo no registrado; elegir al menos un perfil público.

Postcondiciones: Éxito: usuario activo y perfiles seleccionados persistidos; se muestra el acceso. Fallo: no se guarda una identidad incompleta.

Pantallas y salida: /registro → /login

Resumen: El actor inicia registrarse; DayNest valida las condiciones y presenta el resultado descrito en el curso normal.

PasoAcción del usuarioRespuesta del sistema
1Abre el registro.Muestra nombre completo, correo, teléfono opcional, contraseña y perfiles.

PasoAcción del usuarioRespuesta del sistema
